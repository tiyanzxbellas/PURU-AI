# AGENTS.md

## Mulai Cepat
- `go run .` â€” jalankan bot lokal (load `.env` via godotenv)
- `go build -o dist/puru-ai .` â€” kompilasi binary
- `go run ./cmd/cli "pesan..."` â€” chat langsung dengan agent (debug, tanpa Telegram)
- `cli.bat "pesan..."` / `cli.sh "pesan..."` â€” alias cepat ke `go run ./cmd/cli`
- `go vet ./...` â€” static analysis
- `go test ./...` â€” unit test (jsrun, messages, prompt, settings)
- `gofmt -l .` â€” cek format
- Halaman web `/login` memakai **Vite + React** (sumber di `web/`), hasil bundle di-embed ke binary via `go:embed all:dist` di `internal/web/web.go`. Setelah mengubah file di `web/`, build dulu: `cd web && npm install && npm run build` (outDir = `internal/web/dist`; hasil commit wajib ikut di-rebuild supaya `go build`/`go run` tetap jalan). `dist/` (bukan `internal/web/dist`) tetap di-gitignore.

## Konfigurasi & Secrets
- Konfigurasi memakai environment variables, divalidasi saat startup di `internal/config/config.go`.
- File `.env` di root repo hold secrets.
- Firebase RTDB base URL dimuat dari `PUBLIC_RTDB`.
- Konfigurasi opsional (dengan default):
  - `HOSTNAME` â€” alamat bind web/health server (default: `localhost`)
  - `PORT` â€” port web/health server (default: `3000`)
  - `PUBLIC_BASE_URL` â€” URL publik untuk link halaman `/login/{id}/{pw}` (mis. `https://bot.example.com`). Bila kosong, `config.Config.ResolvePublicBaseURL()` default ke `http://localhost:{port}`. `/login` tidak pernah menghasilkan link kosong (dijaga `internal/config/config_test.go`).
  - `TEMPERATURE` â€” temperature model AI (default: `0`)
  - `MAX_LOOP` â€” iterasi maksimal agent per request (default: `20`)
  - `HISTORY_CACHE_MAX` â€” user maksimal di LRU cache (default: `500`)
  - `HISTORY_CACHE_TTL` â€” TTL cache dalam ms (default: `600000`)
  - `MEMORY_UPDATE_EVERY` â€” interval pesan user untuk auto-update MEMORY.md (default: `3`)
  - `MEMORY_MAX_CHARS` â€” cap konten MEMORY.md saat di-inject (default: `8000`)
  - `SCHEDULE_POLL_INTERVAL` â€” interval detik pengecekan scheduler jadwal tugas (default: `15`). Scheduler mengecek task yang jatuh tempo & menjalankannya; hasil dikirim ke private chat user via Telegram.
  - `VISION_MODEL_URL` â€” URL model visi (format Gemini `generateContent`) untuk meringkas gambar yang di-upload user & probe CLI `-image` (default: `https://puruboy-api.vercel.app/api/ai/gemini-v3`).
  - `E2B_TEMPLATE` â€” template sandbox E2B untuk eksekusi kode (default: `code-interpreter-v1`; template `default` lama sudah dihapus dari platform E2B â†’ HTTP 404). Dibaca via `getEnv` di `internal/e2b`, bukan `config.go`.
  - `GITHUB_TOKEN` â€” token GitHub untuk search skill di halaman web (search `filename:SKILL.md`). **Wajib** untuk code search; tanpa token API balas HTTP 401 â†’ hasil search kosong + peringatan.
  - `CLAWHUB_APIKEY` â€” token registry skill ClawHub (opsional). Registry clawhub aktif bila diisi; base URL memakai default (`https://clawhub.ai`).
  - `PROXY_RELAY_URL` â€” base URL relay edge (Vercel/Cloudflare/Deno) ala 9router untuk semua request model OpenAI-compatible (default: relay Vercel built-in, lihat `defaultRelayURL` di `config.go`; dashboard mengekspos toggle **Proxy Relay ON/OFF**). Saat terisi, `internal/ai/openai` mengirim request ke relay root dengan header `x-relay-target` (origin target) + `x-relay-path` (path+query) â€” protokol persis `proxyFetch.js` 9router; relay yang forward method/body/header sisanya. Per-user bisa diatur via toggle **Proxy Relay** di halaman web (tersimpan di `settings/{chatID}.proxyUrl`).

## Arsitektur (Go, module `github.com/purujawa06-bot/PURU-AI`)
- `main.go` â€” entrypoint: config â†’ **servelog buffer dipasang sebagai output log** â†’ web/health server â†’ `getMe` â†’ `deleteWebhook(drop_pending)` â†’ konflict-retry loop (exit setelah 5 conflict berurut). Wiring clientFor memuat `settings.Effective` + kombo aktif (`combosSvc.ModelForActive(ctx, chatID, ai.ComboAttempt(ctx))` — attempt 1-based, jadi setiap retry pindah ke model/provider berikutnya di combo) sebelum `NewModelWithOptions`. Provider **built-in `puru`** di-resolve via `providersSvc.WithBuiltin(BuiltinProvider(cfg.AI))` (katalog model built-in = hanya model default gateway, `cfg.AI.Model`/"puru"); `proxyUrl` provider hanya menimpa bila terisi, sehingga built-in `puru` ikut toggle **Proxy Relay** global/per-user.
- `cmd/cli` â€” debug CLI tanpa Telegram: wiring service sama persis `main.go` (config â†’ firebase â†’ vfs/history/skills/e2b â†’ model â†’ scheduler hooks â†’ memory), lalu `ai.Agent.ProcessMessage` dengan pipeline identik `processMessage` (pruneâ†’capâ†’prosesâ†’persistâ†’memory). One-shot (`cli.bat "pesan"`) atau REPL; chat id debug default `-777` (terpisah dari user publik), flag `-reset`/`-verbose`/`-save-files`/`-no-memory`/`-image <file>` (tes dukungan visi model: kirim satu gambar + prompt ke model, jawaban mentah ke stdout). Dipakai untuk debugging cepat tanpa Telegram.
- `internal/config` â€” config loader.
- `internal/telegram` â€” klien Telegram Bot API **ditulis manual** (poling `getUpdates` synchronous, `sendMessage`, `editMessageText`, `sendDocument/Audio/Video`, `getFile`+download). Sebab utama ditulis sendiri: bot memproses update **sekali-sekali secara beruntun** (satu goroutine) seperti `bot.start()` di grammY, dan deteksi conflict (409) harus presisi. `BaseURL` export sebagai **var** (bukan const) supaya test bisa menunjuk klien ke server mock `httptest`.
- `internal/app` â€” handler bot: dispatcher command + busy-guard per-user (paralel antar-user), pipeline pesan (pruneâ†’capâ†’sanitizeâ†’tokenâ†’memory), safe reply/edit/send, upload dokumen & **pesan foto** (maks 10MB). **Gambar tidak pernah disimpan ke VFS**: dokumen gambar maupun pesan photo (native Telegram `message.photo`) langsung diproses `processImage` (`internal/app/generate.go`) â€” bytes diunduh â†’ `ai.DescribeImage` ke `config.VisionModelURL` untuk ringkasan + teks yang terlihat â†’ hasil di-inject ke agent sebagai user message dengan marker `[context]\n<ringkasan>\n\n<prompt user>` (cap 4k char, dijaga `TestBuildImageContext`); foto dipilih yang beresolusi tertinggi (`largestPhoto`, dijaga `TestLargestPhoto`). File non-gambar tetap disimpan ke VFS dengan inject path-only `[User mengupload file: /{path}]` via `injectUploadedFile` â€” konten tidak pernah di-preview, AI membaca sendiri via `read_file` (dijaga `TestInjectUploadedFile`). **`/ai` khusus grup**: di chat pribadi perintah ditolak (pesan langsung sudah otomatis diproses â€” reply "Tidak perlu /ai..."); di grup dokumen & foto hanya diproses bila caption diawali `/ai` (prefix di-strip, sisa caption menjadi instruksi; upload grup tanpa `/ai` diabaikan â€” dijaga `handlers_test.go`). **Scheduled tasks**: tugas one-shot yang dijalankan agent lalu hasilnya dikirim ke private chat user (chatID == userID). Task disimpan di RTDB `schedules/{id}`, dijalankan saat `runAt` tiba via background scheduler loop (`internal/scheduler`). Prompt task di-inject ulang sebagai user message ke `agent.ProcessMessage` (history kosong, MEMORY.md tetap di-inject). Tugas overdue langsung dijalankan saat bot start; task yang sudah selesai (dan yang dibatalkan) dihapus dari RTDB. Format waktu: RFC3339 dengan offset, datetime naive di timezone, atau time-only (auto-roll ke besok bila sudah lewat). Semua waktu disimpan sebagai epoch UTC; zona waktu default `UTC`.
- `internal/ai` â€” agent tool-loop & sesi dipegang **langchaingo** (`github.com/tmc/langchaingo`): model via **klien OpenAI-compatible sendiri** (`internal/ai/openai`, implementasi `llms.Model`), loop iterasi + scratchpad dikelola `agents.Executor`, sesi di-assemble `prompts.ChatPromptTemplate` (`system` â†’ `chat_history` â†’ `input` â†’ `agent_scratchpad`; system memakai formatter non-templating agar literal `{{name}}` aman), custom `agents.Agent` hanya format prompt + parse output, 27 tools (adapter `tools.Tool` di atas runner lama) + prosesMessage (retry + normalisasi arguments). Tidak ada lagi tool `finish`; jawaban final = teks stop natural executor. Tool scheduler (`schedule_task`/`list_schedules`/`cancel_schedule`) **terdaftar di `BuildTools`** (regresi lama: runner & schema ada tapi tidak masuk daftar `names` â†’ provider balas "not a valid tool"; dijaga jumlah/daftar tool di `internal/ai/tools_test.go`). **Tool-call id di-normalisasi** (`ra.toolID` â†’ `call_<n>` bila provider mengosongkannya, mis. gateway Gemini) supaya pasangan tool callâ†”tool-result selalu 1:1 saat di-replay; history lama tanpa id ikut diperbaiki di `toChatHistory` (perbaikan gemini `400 ... function response parts`). **Model DI-stream** (`stream:true` via `noopStream`) supaya generasi panjang tidak kena timeout gateway 503; assembly tool-call SSE diperbaiki di `internal/ai/openai` â€” langchaingo v0.1.14 hanya menyambung fragment argumen bila delta punya `type` kosong, gateway yang men-tag tiap fragment (`type:"function"`) memecah args jadi tool call kosong (regresi dijaga `internal/ai/openai/openai_test.go` & `internal/ai/agent_test.go`). **Thinking-mode di-thread end-to-end**: `Plan` menyimpan `choice.ReasoningContent` per-step (`ra.recordReasoning`) & per-finish (`ra.lastReasoning`); scratchpad (`stepsToChatMessages`) dan replay history (`toChatHistory`) mengisi `AIChatMessage.ReasoningContent`, lalu `Plan` mengekstraknya ke slice paralel dan memanggil `GenerateContentWithReasoning` (interface lokal `reasoningClient`) supaya `reasoning_content` di-echo ke provider. Persistensi memakai part `reasoning` di `messages.Part` (`responseFromSteps` + jawaban final dipersist sebagai parts `[reasoning, text]`, bukan `SetContentString`); `messages.PruneMessages` tidak pernah membuang part reasoning (regresi: 400 `reasoning_content must be passed back` pada percakapan lanjutan / iterasi tool-loop berikutnya; dijaga `agent_test.go`, `session_test.go`, `openai_test.go`, `messages_test.go`). **Model build & relay**: `ai.NewModelWithOptions(ModelOptions{...})` meneruskan `Headers` (header ekstra provider), `Proxy` (relay URL) & `Session` (id stabil per-chat via `ai.ChatSessionID(chatID)` = `ses_<sha256(chatID)>`) ke klien; `clientFor` di `main.go`/`cmd/cli` memakainya dari `settings.Effective` sehingga template provider (mis. OpenCode Free) + toggle proxy relay per-user langsung berlaku.
- `internal/ai/openai` â€” klien OpenAI-compatible minimal (implementasi `llms.Model.GenerateContent`): SSE streaming benar, fallback non-SSE untuk proxy yang membalas JSON biasa walau `stream:true`, dan **assembly tool-call yang diperbaiki** (fragment argumen di-append ke tool call pada index yang sama, bukan jadi tool call baru â€” lihat `mergeToolCallDeltas`). **Thinking-mode (`reasoning_content`) didukung**: SSE/JSON delta menangkap `reasoning_content` ke `llms.ContentChoice.ReasoningContent`, dan method `GenerateContentWithReasoning(ctx, msgs, reasonings, opts...)` menyisipkan reasoning per-pesan (index-aligned) kembali ke wire sebagai `reasoning_content` â€” dipakai agar provider ala deepseek-reasoner tidak 400 `The reasoning_content in the thinking mode must be passed back to the API`; `GenerateContent` lama mendelegasikan dengan `reasonings=nil` (tanpa reasoning). **Visi (image input) didukung**: `llms.BinaryContent` diserialisasi ke content array OpenAI vision (`[{"type":"text",...},{"type":"image_url","url":"data:<mime>;base64,..."}]`), mime di-sniff dari magic bytes bila kosong (`sniffImageMIME`); respons tetap di-parse dengan struct `wireRespMessage` ber-content string murni â€” dijaga `openai_test.go` (`TestContentToStringImage`). Catatan: model `puru` di gateway bawaan **tidak mendukung gambar** (probe `cli -image` menjawab "tidak bisa melihat gambar"); visi di-handle terpisah oleh `ai.DescribeImage` ke `config.VisionModelURL` (lihat `internal/ai/images.go`). Konsisten etos repo: klien Telegram & E2B juga ditulis manual. **Header ekstra & relay**: `NewWithOptions(Options{Headers, Proxy, Session}, hc)` (konstruktor `New` tetap ada). Saat `Proxy` terisi, `roundTrip` mengirim request ke relay root + header `x-relay-target` (skema://host target asli) + `x-relay-path` (path+query) â€” protokol persis `proxyFetch.js` 9router; relay memforward method/body/header lainnya. Header ekstra di-set ke tiap request, dengan marker `@session` â†’ `Session` (id stabil per-chat) dan `@request` â†’ `msg_<hex random>` fresh per HTTP call (dijaga `TestExtraHeadersAndSessionMarker`, `TestRelayProxy`, `TestRelayProxyIgnoresOrigin`).
- `internal/ai/images.go` â€” klien **model visi** (format Gemini `generateContent`): `DescribeImage(ctx, hc, endpoint, prompt, image, mime)` mengirim `contents[].parts` berisi teks + `inlineData` base64 lalu mem-parse `candidates[].content.parts[0].text` (error HTTP non-200/`error`/tanpa kandidat dilaporkan jelas). Endpoint dari `config.VisionModelURL` (env `VISION_MODEL_URL`, default `https://puruboy-api.vercel.app/api/ai/gemini-v3` â€” gateway Gemini; bila gateway down, error "HTTP 5xx"). `IsImageContent` (export wrapper `sniffImageMIME`) dipakai `internal/app` untuk mendeteksi file upload yang berupa gambar. Dijaga `images_test.go` (`TestDescribeImage*`, `TestSniffImageMIME`). **Tool `read_image` dihapus** â€” gambar tidak lagi disimpan ke VFS, melainkan diringkas saat upload (alur `processImage` di `internal/app`); `resolveImageData`/`decodeImageContent` (bantu read_image lama) ikut dihapus.
- `internal/messages` â€” model pesan `ModelMessage` kompatibel dengan schema Vercel AI SDK (round-trip field tak dikenal dipertahankan) + port `pruneMessages`/`EnsureStartsWithUser`/`CapUserTurns`/`Sanitize`. `PruneMessages` **tidak pernah membuang part `reasoning`** (dipakai thinking-mode provider; lihat `internal/ai`); `SanitizeMessage` memotong teks part `reasoning` di `MaxStoredContent` seperti text.
- `internal/firebase` â€” helper REST ing RTDB (GET/PUT/PATCH/DELETE `.json` + base64url path) + `ListKeys` (shallow `?shallow=true`) untuk enumerasi key anak sebuah node â€” dipakai `VFS.DeleteDir` agar pembersihan tidak bergantung pada index (RTDB eventual consistency bisa membuat index stale). `Patch` (HTTP PATCH) hanya merge data tanpa menghapus child node â€” wajib dipakai oleh index write (`vfs.writeIndex`) agar node index per-direktori di bawah `fs/{id}/index` tidak terhapus setiap kali index root ditulis ulang (PUT di RTDB mengganti seluruh node, termasuk children; regresi: semua folder VFS tampil kosong di halaman web).
- `internal/settings` â€” config API per-user (base URL/key/model/**systemPrompt**) di RTDB `settings/{chatID}` (partial override; field kosong = inherit global) + cache TTL in-memory. `Effective(global, user)` menggabungkan override base URL/key/model/**proxyUrl**/**headers**; `SystemPrompt` bukan bagian model config â€” di-inject terpisah di `ai.Agent.ProcessMessage` (di-append ke system prompt bawaan dengan header `# User-defined instructions`). Field tambahan: `proxyUrl` (nil=ikut global, `""`=paksa langsung, terisi=relay URL) & `headers` (map header ekstra, mis. `x-opencode-*`; nilai `@session`/`@request` jadi marker yang di-substitusi klien per-chat/per-request).
- `internal/vfs` â€” virtual file system per-user di RTDB. `ReadFile` memperlakukan respons RTDB literal `null` sebagai file **tidak ada** (return `false`); tanpa pengecekan ini, `json.Unmarshal("null", &string)` diam-diam menghasilkan file "ada tapi kosong" dan membuat install skill salah melaporkan "sudah terinstall". `DeleteFile` punya guard `null` yang sama â€” file yang tak ada dilaporkan `false` (tidak ada), bukan sukses palsu (regresi `delete_file` phantom-success; dijaga `vfs_test.go`). `DeleteDir` menghapus sebuah direktori beserta seluruh isinya dengan **memindai store `content/` dan `index/` langsung** (via `firebase.ListKeys` shallow), bukan menelusuri index direktori â€” sehingga tetap bersih walau index rusak oleh race read-modify-write RTDB saat install (mis. entri `SKILL.md` hilang dari index `skills/pdf` tapi file content-nya masih ada; regresi `delete_skill` yang hanya menghapus `SKILL.md` meninggalkan scripts/`.skill-origin.json` yatim; dijaga `vfs_test.go` & `manifest_test.go`).
- `internal/history` â€” persistensi history (LRU+TTL + RTDB; hasil copy bukan mutasi cache).
- `internal/usage` â€” per-request token usage per-user di RTDB `usage/{chat}/logs/{key}` untuk halaman web **Usage** ala 9router. Setiap jawaban model (teks/dokumen/foto â€” 3 titik `SetTokens` di `internal/app/generate.go`) dipanggil `App.recordUsage` â†’ `usage.Manager.Add` dengan provider label (host `baseUrl`) + model efektif + input/output token. Key pakai **reverse-epoch** (`math.MaxInt64 - unixMs`) supaya string sort = urutan waktu (terbaru dulu); `prune` memakai `firebase.ListKeys` shallow untuk membuang yang melebihi `MaxRecords` (500). `Summarize` mengagregasi total request/input/output.
- `internal/servelog` â€” ring buffer in-memory (cap 1000) untuk **Server Logs**. `main.go` pasang `log.SetOutput(io.MultiWriter(os.Stderr, buffer))` sehingga semua `log.Printf` (bot, ai, app, scheduler) ikut tertampung; dashboard polling `GET /api/logs` tiap 2 detik. `Clear` membuang isi; `POST /api/logs` (clear).
- `internal/combos` â€” kombo model per-user (nama + daftar model, strategi **hanya fallback**) disimpan di RTDB `combos/{chat}` (daftar combo di child `items`, marker `active` di sibling `active` — keduanya terpisah sehingga PUT daftar tidak menghapus marker aktif & SetActive tidak mengubah node list jadi object yang gagal di-parse sebagai slice; layout lama array-di-akar saling menimpa → combo "hilang"/aktif terhapus, migrasi otomatis `migrateLegacy` + recovery mixed-node `extractComboList`, dijaga `combos_test.go`). CRUD web: `GET/POST /api/combos`, `POST /api/combos/activate`, `POST /api/combos/delete`. Saat kombo `active`, `clientFor` (`main.go` & `cmd/cli`) menimpa nama model: `ModelForActive(ctx, chatID, attempt)` memilih `combo.Models[attempt-1]` (attempt 1-based dari `retryLoop` via `WithComboAttempt` context; lewat dari jumlah model tetap memakai model terakhir — tidak wrap-around ke model pertama, dijaga `combos_test.go`). **Logika retry kombo dipindah ke `internal/combos`**: saat kombo aktif, `retryLoop` di `internal/ai/agent.go` berjalan maksimal `max(MAX_LOOP-retry=4, jumlah model combo)` attempt dan **setiap kegagalan — termasuk error 4xx non-retryable — memajukan ke model/provider berikutnya di combo** (provider yang berbeda tetap bisa sukses); tanpa kombo, error 4xx/`errNoModel` tetap fatal (break retryLoop). `Upsert` memaksa `strategy = fallback` (nilai round-robin/fusion lama di data tetap terbaca tapi dianggap fallback). Combo model kini biasanya memakai ref `prefix/model-id` (dipilih dari catalog online provider lewat `ModelSelectModal`), tapi model polos lama tetap valid.
- `internal/providers` â€” registry provider per-user ala 9router "OpenAI Compatible nodes" (Anthropic-compatible **dihapus** — hanya OpenAI-compatible), disimpan di RTDB `providers/{chat}` (`Provider{ID,Name,Prefix,Type(openai-compatible|anthropic-compatible),APIType(chat|responses),BaseURL,APIKey,Headers,ProxyURL,Model}`; API key **tidak pernah dikembalikan** ke web â€” `PublicList` hanya mengekspos flag `hasApiKey`). `CheckStored`/`CheckInline` mengambil **catalog model live** `GET {baseUrl}/models` (strip trailing `/`, anthropic buang suffix `/messages`; parse `data.data || data.models` + array polos id-string; header auth `Authorization: Bearer` / `x-api-key`+`anthropic-version 2023-06-01`; bila `ProxyURL` terisi request lewat relay 9router dengan `x-relay-target`/`x-relay-path`; cache in-memory `ModelCacheTTL` 60s) â†’ `ModelsResult{Online,Status,LatencyMs,Error,Models}`. **Provider built-in `puru` TIDAK fetch `/models`** â€” `fetch` short-circuit untuk `p.Builtin` mengembalikan katalog berisi satu model default gateway (`p.Model`, = `cfg.AI.Model`/"puru") dengan status selalu online, sehingga list model built-in hanya "puru". `SplitModelRef` memecah `prefix/model-id`; `Resolve(chatID, ref)` mengembalikan `(Provider, model)` bila prefix terdaftar (nil bila ref polos/prefix tak dikenal â†’ fallback ke `settings.Effective`). `Referencing(prefix, model)` dipakai web saat provider dihapus untuk membersihkan ref `prefix/` di `settings.model` & model combo. **Provider built-in `puru`** (prefix `puru`, ID `builtin-puru`, `BuiltinProvider(cfg.AI)`) = gateway default server yang selalu tampil di list/picker (list & dapat dipakai di combo via `Resolve`) dan **tidak bisa dihapus/diubah** (prefix `puru` di-reserve di `Upsert`, delete ditolak; dijaga `providers_test.go` & `web_test.go`). Dijaga `providers_test.go` (httptest upstream + relay + non-2xx + parse shapes).
- `internal/tokens` â€” wrapper tiktoken-go (`o200k_base`).
- `internal/skills` â€” parsing SKILL.md (frontmatter) + registry manager yang **mengimpor logika `pkg/skills` picoclaw** (`github.com/sipeed/picoclaw/pkg/skills`). Search memakai **GitHub code search** `GET /search/code?q=<query> filename:SKILL.md` (dedup per slug `owner/repo[/subdir]`, sort by score, clamp 20; 401/403 â†’ hasil kosong + warning) + registry ClawHub via `RegistryManager.SearchAll` (fan-out concurrent, semaphore, merge by score). **Hasil antar-registry di-interleave round-robin, bukan merge sort skor global** (`interleaveByRegistry`): skor GitHub code search ~1 vs ClawHub ribuan, sehingga merge skor global membuat GitHub selalu tersingkir sebelum clamp top-20 (regresi: hasil `/skills search` hanya berisi ClawHub, GitHub tidak pernah muncul; dijaga `registry_test.go`). ## Perilaku Penting (dipertahankan dari generasi sebelumnya)
- **Retry**: API call retry hingga 4 kali dengan exponential backoff (1sâ†’2sâ†’4sâ†’8s, cap 30s). Error 4xx selain 408/429 TIDAK di-retry (`isNonRetryableError`) - kecuali saat kombo (fallback) aktif: error apapun (termasuk 4xx) memajukan retry ke model/provider berikutnya di combo (attempt bisa lebih dari 4 bila jumlah model combo lebih besar; logika di `internal/combos`). Web search retry 5 kali (1sâ†’16s, cap 30s).
- **Diagnostik error agent** (`agent.go`): bila jawaban gagal â€” `ToolsBuild` error, model tidak tersedia (`errNoModel`), `GenerateContent` error, `empty model response` (tanpa `choices`), atau final teks kosong â€” penyebabnya SELALU di-log dengan prefix `[ai]` (per-attempt, `finish_reason`, alasan akhir). Sebelumnya `lastErr` dibuang diam-diam (`_ =`) sehingga "API sukses tapi bot diam" tak terbaca. Kondisi pasti-gagal (`isNonRetryableError`/`errNoModel`) langsung `break retryLoop` pada model tunggal tanpa kombo; saat kombo (fallback) aktif, kegagalan apapun (termasuk 4xx) justru memajukan retry ke model/provider berikutnya di combo. Hanya error transien & empty-text yang di-retry (tanpa kombo). User tetap mendapat fallback pendek `Maaf, saya tidak bisa merespons saat ini.`
- **User-Agent browser** (`main.go`): shared `http.Client` memakai transport yang menyuntikkan UA Chrome bila header kosong â€” supaya `crawl` tidak ditolak HTTP 403 oleh situs seperti Wikipedia yang memblokir `Go-http-client/1.1`. Header UA eksplisit (mis. e2b `puru-ai/1.0`) tetap menang.
- **Timeout agent** (`agent.go`): total 300s via `context.WithTimeout`; per-tool 120s (`toolTimeout`) di adapter `tools.Tool`; model dipanggil streaming (`GenerateContent` + `WithStreamingFunc(noopStream)`) â€” assembly tool-call SSE diperbaiki di `internal/ai/openai` (klien langchaingo v0.1.14 memecah fragment argumen ber-`type:"function"` jadi tool call kosong). **Context tool WAJIB tetap hidup** â€” langchaingo `agents.Executor` tidak membatalkan ctx di antara langkah tool; regresi lama (`cancel()` prematur setelah Chat membuat semua tool HTTP gagal `context canceled`) dijaga oleh `internal/ai/agent_test.go`.
- **Batas data**: crawl baca body max 1.5MB & hasil max 20k char (tool), `read_file` max 30 ribu char; upload dokumen max 10MB; isi history di-truncate max 8k char/message (`messages.Sanitize`).
- **Persistensi history**: path `history/{chat}/messages|tokens|meta` di RTDB, LRU+TTL di dalam proses (hasil getHistory berupa copy; array kosong tidak di-cache). JSON schema = `ModelMessage` Vercel AI SDK v7 â†’ data user lama tetap terbaca & round-trip field tidak hilang.
- **Batas history**: sebelum dikirim ke model, history di-prune (`toolCalls: before-last-6-messages`, kosong dihapus) lalu di-cap maksimal 5 pesan user (`messages.CapUserTurns`). Part `reasoning` TIDAK pernah di-prune â€” provider thinking-mode (deepseek-reasoner dkk) mewajibkan `reasoning_content` tiap pesan assistant yang di-replay di-echo kembali (400 `must be passed back` bila hilang).
- **Conflict loop** (`main.go`): conflict beruntun â‰¥5 â†’ `os.Exit(1)` agar platform restart bersih.
- **Pemrosesan paralel per-user** (`internal/app/app.go`): `Handle` hanya dispatcher â€” setiap update text/document dijalankan di goroutine sendiri sehingga semua user diproses bersamaan tanpa antrian. User yang sama dikunci via `busy sync.Map` (`tryAcquire`/`release`): update kedua saat request masih berjalan langsung dibalas `â³ Masih ada yang lagi diproses, tunggu sebentar ya...` (tidak di-queue). **Busy guard hanya berlaku untuk pesan AI** (teks polos, `/ai`, dokumen) â€” command non-AI (`/menu`, `/clear`, `/reset`, `/login`, `/pw`, `/token`, `/info`, dst.) SELALU langsung dieksekusi tanpa diblok busy. `/config` & `/skills` tidak lagi terdaftar â€” pengguna yang mengetiknya diarahkan ke `/login` (halaman web). Command token dinormalisasi (`splitCommand`) dengan strip suffix `@bot` sehingga `/menu@nama_bot` di grup tetap dikenali; subcommand membaca argumen dari sisa token, bukan `msg.Text[len("/cmd"):]`. Konsistensi per-user (history/LRU/e2b) aman karena dua request user yang sama tidak pernah bersamaan; `main.go` hanya memajukan offset, error async hanya di-log.
- **Anti-halusinasi & protocol guard** (`internal/ai/agent.go`): system prompt melarang klaim tanpa tool call & filler; loop iterasi dikelola langchaingo `agents.Executor` (`MAX_LOOP` = `WithMaxIterations`). Jawaban final = teks stop natural executor (tidak ada lagi tool `finish`/scold-correction). Loop yang habis (`agents.ErrNotFinished`) â†’ hint step-limit `lanjut`. Hanya turn yang menghasilkan teks non-kosong yang dipersist (`runOnce` menambahkan assistant-final ke `responseMessages`; output kosong tidak pernah ikut tersimpan â€” regresi polusi stub dijaga `internal/ai/agent_test.go`); `messages.SanitizeHistoryMessages` tetap membuang text part kosong/whitespace & pesan assistant kosong tanpa tool-call; `makeResult` fallback ke pesan error bila teks kosong. `arguments` tool call dinormalisasi (`toolArgsJSON`) sebelum replay ke provider agar provider ketat tidak menolak. Di `internal/prompt`: Rule 9 â€” bila pesan user ambigu/pendek/gibberish, AI dilarang menebak dengan tool dan wajib tanya klarifikasi langsung (dijaga assertion `prompt_test.go`).
- **Elusive memory**: auto-update `/memory/MEMORY.md` setelah `MEMORY_UPDATE_EVERY` pesan user (counter `history/{id}/meta`), error non-fatal. MEMORY.md dikelola sistem, AI dilarang baca/tulis sendiri. Konten di-update agar **minimal**: maks 5 poin penting bernomor + baris `Topik sedang dibahas:`; info usang/irrelevan dihapus (`memoryPrompt`, cap output 1500 char).
- **Safe reply/edit**: fallback parse-mode Markdown bila Telegram menolak entitas parse; respon >4096 char dikirim sebagai file. Semua teks keluar (sendMessage/editMessageText/caption) di-sanitasi jadi valid UTF-8 via `sanitizeText` (`strings.ToValidUTF8`, U+FFFD) di `internal/telegram` agar tidak kena `400 text must be encoded in UTF-8` bila output model/scraped berisi byte invalid.
- **Jawaban final pesan baru**: jawaban AI dikirim sebagai **pesan baru** (reply ke pesan user) via `safeSend`, bukan edit â€” placeholder "ðŸ¤” sedang berpikir..."/pesan "Tersimpan di /path..." dihapus via `deleteMessage` setelah jawaban terkirim (`internal/app/generate.go`).
- **Per-user API config via web**: `/config` & `/skills` dihapus dari Telegram â€” diganti alur `/pw <password>` (simpan kredensial login web di `auth/{chatID}`) lalu `/login` (keluarkan link `https://{PUBLIC_BASE_URL}/login/{id}/{pw}`; bila `PUBLIC_BASE_URL` kosong default ke `http://localhost:{port}`, lihat `config.Config.ResolvePublicBaseURL()`). Pengaturan API (base URL/key/model/system prompt) & manajemen skills (list/search/install/delete) dikelola lewat halaman web tersebut. Partial override global via `settings.Effective` tetap dipakai; resolver `ClientFor(ctx, chatID)` membuat model langchaingo `llms.Model` fresh per request (pakai http.Client global) â‡’ aman paralel. Memory update juga ikut API user. Path `settings/{chatID}` di RTDB terpisah dari `fs/` & `history/` sehingga `/reset chat` tidak menghapus config; `auth/{chatID}` juga terpisah sehingga password tidak ikut terhapus.
- **/reset terpisah**: `/reset` polos = help; `/reset config` hapus settings user (beserta systemPrompt â€” beda dari Reset web yang memakai `DeleteKeepPrompt` dan mempertahankan systemPrompt); `/reset memory` hapus MEMORY.md + reset counter `meta.userTurns`; `/reset chat` = `DeleteHistory` + `vfs.DeleteAll` (perilaku /reset lama).
- **E2B**: satu sandbox per chat, TTL 5 menit idle, auto-kill; `runCode` hasil NDJSON `{type: stdout/stderr/result/error}`.
- **Math & crawl**: evaluasi lewat goja. `calculate_math` menyediakan alias Math (`sqrt`, `pow`, ...). Hasil non-finite (Infinity/NaN, mis. `10/0`) ditolak sebagai error "Ekspresi matematika tidak valid" â€” tidak dikembalikan ke model (regresi; dijaga `jsrun_test.go`). `crawl` mengharapkan snippet cheerio JavaScript (shim compat: `text`, `html`, `attr`, `val`, `length`, `first`, `last`, `eq`, `find`, `parent`, `parents`, `children`, `filter`, `next`, `nextAll`, `prev`, `prevAll`, `siblings`, `closest`, `each`, `map`, `get`, `toArray`, passthrough `$(el)`; `map` mengembalikan wrapper yang mendukung `get()`/`toArray()`/`slice()`/`join()` sehingga idiom `.map(...).get()` gaya cheerio berfungsi, `get()` tanpa argumen = array semua text); snippet boleh ekspresi atau statement `return {...};` (`normalizeCheerioCode` men-strip leading `return` + trailing `;` sebelum di-wrap evaluator, dijaga `jsrun_test.go`). URL crawl di-normalisasi dulu (`normalizeURL` di `internal/ai/tools.go`): url kosong/invalid/skema non-http(s)/host kosong mengembalikan error jelas (bukan `unsupported protocol scheme` mentah dari `http.Client`), url tanpa skema diberi prefix `https://`; dijaga `tools_test.go`.
- **Tool schema**: `required` di function schema hanya disertakan bila ada (dihilangkan saat kosong) â€” provider OpenAI-compatible tertentu menolak `"required": null`; dijaga `internal/ai/tools_test.go`.
